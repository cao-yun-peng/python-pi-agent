基础依赖的目标方向：实现 → 协议 → 领域对象。当前源码大体遵循该方向，具体例外见第 04 节。

application：把零件组装成可用产品

builder.py 事务化创建 Provider、Store、插件与观察设施；runtime.py 管 Session 池和租约；lifecycle.py 区分 owned / borrowed，失败时回滚。这里依赖具体实现属于合理的组装职责。

runtime：一次运行与一个会话分开

loop.py 执行一次 run；session.py 恢复历史、装配 Agent 和插件 lease；control.py 管 FIFO、steer、follow-up 与 abort；压缩另有编排模块。运行层与应用 facade 有不同生命周期。

domain + ports：共同语言与替换接口

domain 提供消息、工具、事件和状态值对象；ports 定义 ModelProvider、SessionStore、ContextStrategy、ApprovalPolicy 等 Protocol。实现可以替换，但替换者必须满足相同语义。

storage + context：事实与模型视图分开

durable log 记录可恢复事实，replay 重建 snapshot。ContextStrategy 投影当次请求；CompactionStrategy 生成摘要，Session 编排持久化。“少给模型一些历史”和“持久替换历史”属于不同机制。

providers：协议转换与请求韧性分开

各供应商隔离认证、wire protocol 和完成判据；codec 复用通用协议片段。providers/runtime.py 消费 ModelProvider，组合路由、重试与回退，不让 Agent loop 识别供应商。

tools / plugins / observability：扩展与观察分开

工具通过协议执行，PluginHost 事务化发布能力并管理 cleanup；观察事件隔离失败，middleware 则显式影响请求或结果。观察队列可丢失，不能承担恢复事实。

04值得调整的是局部边界

以下是维护性建议，不是已证实的运行故障。P1 表示近期值得处理，P2 表示随真实扩展推进；仅用于本次评审排序。

P1

让“端口只依赖领域”在类型层面也成立

观察：ports.py 的 TYPE_CHECKING 分支引用 runtime.session_spec.SessionSpec，以及 providers.runtime 中的 AttemptFailure、ProviderCandidate、RetryDecision。接口签名依赖上层定义，与架构文档中“ports 只依赖 domain”的规则有差距。

影响：TYPE_CHECKING 避免这些导入在运行时执行，因此这不是已发生的循环导入故障；但改动运行层类型时仍需联动端口，理解基础契约也需要跳到实现目录。

建议：优先提取模型路由的纯契约 DTO，保持公开导出身份与兼容性。SessionSpec 包含 AgentComponents，不能简单搬进 domain；可将会话选择契约明确归于 runtime，或将组件规格一并抽离到不依赖执行器的契约模块。先选择完整方案。
证据：ports.py:8–14、52、74、90；SessionSpec；模型路由 DTO。验收：类型检查分支也满足依赖规则，公开 API 和行为测试保持通过。
P1

把依赖方向变成可执行检查

观察：已读的 test_api.py 验证导出身份、旧模块移除与下游用法；pyproject.toml 的 strict mypy 只列出选定模块，未完整覆盖 application 与核心编排模块。API 稳定和依赖方向需要不同证据。

建议：在现有测试旁增加轻量 AST 导入约束，先保护 domain 不依赖 runtime、ports 不引用具体实现、runtime 不依赖 application 或具体模型供应商。把默认实现依赖列为明确例外，再逐步收敛；分批扩大 mypy 范围。

已有目录布局足够清晰。接下来更有价值的是防止新能力重新穿透边界，无需为此引入大型架构框架。
证据：test_api.py；tool.mypy.modules。本次未完整检索所有测试，不断言仓内完全没有其他依赖检查。验收：故意加入违规导入时检查能够失败。
P2

明确默认策略属于哪里

观察：runtime/components.py 直接导入 FullHistoryContextStrategy、DenyByDefaultApprovalPolicy、DeclaredSideEffectGate 和 SubsetSchemaValidator，用 default_factory 创建实例。消费点依赖协议，但规格的默认构造仍选择具体实现。

判断：这些默认值安全且方便教学，暂时没有必须调整的证据；但当前结构应准确描述为“端口优先 + 内置安全默认”，并非完全严格分层。

建议：先在架构文档明确允许这个例外。若多个产品 Profile 对默认值产生竞争，再把默认创建收敛到 Profile/Builder，同时保留清楚的最小构造体验。
证据：components.py:63–71。验收：默认拒绝策略不变，自定义策略无需改 runtime，已有组件契约保持稳定。
P1

清理文档的新旧状态混排

观察：architecture.md 的 MCP 阶段 1 段仍写 SDK owner、stdio/HTTP、YAML 等“尚未实现”，后续阶段又记录完成；roadmap.md 的历史差距表还列着旧模块路径和已修复问题，后文才更新状态。

影响：读者可能误以为缺少 InternalError、AgentComponents 或 run 订阅，重新规划已完成的工作。对教学项目，这会直接影响架构的可理解性。

建议：文档开头给出当前能力摘要，将历史阶段显式标注为历史记录；差距表逐项显示“完成 / 部分完成 / 待实现”，保留 ADR 与提交追溯，更新旧路径。
证据：architecture.md 的 MCP 阶段 1–4；roadmap.md 差距表与后续进展。验收：同一能力不再同时被读成“缺失”和“完成”。本次未改动这些现有文件。
P2

按变化原因拆热点文件

观察：当前 loop.py 为 1,011 行、plugins.py 为 972 行、domain.py 为 1,165 行，含空行和注释。loop.py 仍同时承载模型流归一化与工具调度细节。

建议：暂时保留布局。只有工具执行链持续扩展、与模型流频繁独立变化时，再抽出 ToolExecutor 一类内部协作者；领域对象也应按稳定概念拆分，而非按行数机械切割。

证据：loop.py:345 的 _request_model；605 的 _execute_tool_calls。验收应覆盖事件顺序、取消传播、逐消息提交和 unknown 副作用语义。跨目录私有 writer / event helper 目前可视为包内协作，不必立即新增公共端口。

明确触发条件再投入

规模与部署变化后的演进

  • 多进程共享日志：JSONL 的实例级 asyncio.Lock 不提供跨进程互斥，需要存储事务或跨进程锁。
  • 历史持续增长：JSONL 多项操作重读全量事件；测得瓶颈后再做索引、快照或 SQLite 实现。
  • 独立发布需求：组件需要独立版本时再拆包；现有单包加功能目录符合仓库原则。
  • 明确并发需求：工具并行、插件热重载要与隔离、取消和卸载语义一起设计。

存储判断来自 JsonlSessionStore 的实例锁、_read_all_events 与 append 路径，以及 architecture.md 已记录的限制。本次未测试性能，不将其描述为当前性能故障。

06推荐源码阅读顺序

  1. 对象与协议domain.py → ports.py → runtime/components.py。理解核心运行需要哪些事实和能力。
  2. 最小循环runtime/loop.py → test_minimal_loop.py。跟踪消息何时提交、失败与取消如何 settled。
  3. 会话与恢复runtime/session.py → control.py → storage/_writer.py → transitions.py。区分控制、持久提交和回放。
  4. 应用与扩展application/builder.py → profiles.py → lifecycle.py → plugins.py，再挑 MCP 或 read 验证能力接入路径。
